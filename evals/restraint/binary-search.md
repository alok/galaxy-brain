**Θ(log n) comparisons, worst and average case.** Worst case is exactly ⌈log₂(n+1)⌉, which matches the decision-tree lower bound. In the comparison model, binary search is optimal.

No clever reframe overturns that. The non-obvious part is what the bound assumes: unit-cost random access and unit-cost comparisons. Drop either assumption and the answer changes.

- **Memory hierarchy.** Take n = 10⁹ four-byte ints, a 4 GB array: about 30 probes. Only the last ~4 share a 64-byte cache line, so a cold query touches about 26 distinct lines, and the deep ones are mostly cache or TLB misses. In external-memory terms that is Θ(log₂(n/B)) transfers, where log_B n is achievable. A B-tree or van Emde Boas layout gets there. So does an Eytzinger (BFS-order) layout with prefetching, which in practice beats plain sorted-order binary search by a constant factor of a few on large arrays (Khuong & Morin 2017). Same O(log n) on paper, very different wall time.
- **Branch prediction.** Each comparison is close to a fair coin, so a branchy loop mispredicts about half the time. While the array fits in cache, a branchless version (cmov, fixed iteration count) is often faster even though it does the same number of comparisons.
- **Comparison cost.** If keys are strings of length m with long shared prefixes, each comparison costs O(m), giving O(m log n) in total. Suffix arrays with LCP information bring this down to O(m + log n) (Manber & Myers). The "log n" was only ever counting comparisons, not time.
- **Integer keys.** Once you use the bits of the keys instead of only comparing them, you leave the comparison model and the Ω(log n) bound no longer applies. Interpolation search runs in O(log log n) expected time on uniformly distributed keys, and degrades to O(n) on adversarial ones. If you may build a small index or reorder the array, predecessor structures (van Emde Boas trees, fusion trees) beat log n. Pătraşcu & Thorup worked out the tight trade-offs.
- **Access model.** The bound is sublinear only because random access costs O(1). On a linked list or a tape it is Θ(n) to reach the middle, so "binary search is O(log n)" is really a statement about the RAM model.

Short version: log n counts comparisons, and only comparisons. On real hardware, cache-line transfers and mispredictions dominate the cost, and the data layout matters more than the algorithm.
